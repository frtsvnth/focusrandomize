# Спецификация: следующее поколение Sprint Review Show

> Черновик для нового отдельного репозитория. Документ рассчитан на то, что его
> откроет Claude Code (или другой агент) без контекста этого обсуждения — поэтому
> здесь есть и «зачем», и «что именно», а не только тезисы.

## 1. Контекст

Текущий проект (`focusrandomize`, product-имя «Sprint Review Show») — статический
SPA-инструмент для гейміфицированного выбора очередности команд на Sprint Review:
14 визуальных механик отбора (колесо, гонки, лабиринт и т.д.), presenter-режим для
шаринга экрана, admin-панель, 5 тем, звук, localStorage-хранилище.

Рыночный вывод из ресёрча: инструменты-рандомайзеры (Wheel of Names и клоны) — это
голый спиннер без шоу; scrum-тулы (Geekbot, Standuply, Parabol) — геймификация без
визуального шоу. Никто не соединяет «инструмент ритуала» с полноценным зрелищем
(сюжет, саспенс, 3D, звук). Это и есть актив, который новая архитектура должна
защищать и усиливать.

**Решение:** новый проект — отдельный репозиторий, где презентационный слой
(обвязка, оркестрация показа, разделение ролей) переделывается первым, а сами
механики переносятся позже, по одной, на новый фундамент.

## 2. Архитектурные решения (взяты за основу — «вариант Б»)

1. **Единая show-machine.** Весь цикл показа (`idle → prerolling → animating →
   revealing → cleared`) — один явный state machine (state и переходы описаны в коде
   декларативно, кандидат — XState), а не смесь reducer-state и локального
   `useState` компонента, как сейчас. Это убирает класс багов рассинхрона
   анимации/результата, который уже проявлялся в текущем репо (hideSeek: «seeker
   turns before found»).
2. **Один движок механик.** V1 отбрасывается, остаётся только V2-подход (канвас/
   Three.js/Phaser, частицы, процедурный звук). Дублирование адаптеров и
   `MECHANIC_META` на два движка — не нужно.
3. **Presentation kit.** Частицы, canvas-утилиты, звуковой движок, темы — общий
   внутренний пакет с явным API, а не россыпь утилит внутри `mechanics-v2/engine`.
4. **Manifest-регистрация механик.** Каждая механика регистрируется одним файлом
   (id, метаданные, превью, точка входа), без правок в нескольких местах при
   добавлении новой.
5. **Room/session слой (новое).** Единый real-time «канал показа» — по коду сессии,
   без обязательной привязки к аккаунту. Изначально нужен для зрительской страницы
   (п. 4 ниже), но спроектирован достаточно универсально, чтобы позже тем же
   каналом мог быть пульт ведущего с телефона — это один и тот же transport
   (typed pub/sub поверх WebSocket), а не две отдельные подсистемы.

Бэкенд теперь допустим (пользователь готов развернуть на своём VPS) — это снимает
прежнее ограничение «только статический SPA» и открывает real-time функциональность.

## 3. Что переносим из текущего репозитория как есть

- `domain/schema.ts` + zod-валидация — модель данных проверенная, менять не за чем.
- `engine/selectionEngine.ts` — чистая логика выбора команды, уже покрыта тестами.
- Идея адаптерного контракта механики: `{ teams, targetTeam, seed, reducedMotion,
  onComplete }` — простой и удачно спроектированный интерфейс, сохраняем как базу
  нового manifest-формата.
- Ассеты и их пайплайн (Kenney-модели + CREDITS-файлы).

Всё остальное в презентационном слое — оркестрация показа, admin/controller UX,
V1/V2 развилка — пишется заново под новую архитектуру.

## 4. Фазы разработки

### Фаза 1 — MVP нового репозитория (делаем в первую очередь)

Именно то, что попросил заказчик как обязательное «прямо сейчас»:

- Show-machine + унификация движка механик (п. 2.1–2.3 выше), перенос 2–3 самых
  сильных механик как первый вертикальный срез (не все 14 сразу).
- **Полная переработка главного экрана ведущего** — см. отдельный дизайн-бриф
  в разделе 6. Это первый видимый результат нового проекта.
- Admin-панель — минимальный перенос текущей функциональности (команды, сценарий
  очерёдности, темы, бэкап), без новых фич.
- Деплой: фронт может остаться статикой (GitHub Pages/Vercel), бэкенд для
  real-time — пока не обязателен, если Фаза 2 не стартовала одновременно.

### Фаза 2 — интерактивный слой и профиль ведущего

- **Зрительская страница** (`/join/<code>` или аналог) — участники команд, которые
  сейчас не выступают, заходят с телефона по коду сессии (без обязательной
  регистрации) и могут:
  - отправлять реакции (эмодзи-вспышка), которые всплывают на главном экране;
  - (опционально, за флагом в админке — см. открытые вопросы) ставить оценку
    выступлению;
  - после ceremony — видеть результаты/историю сессии.
  Технически: room/session слой из п. 2.5, WebSocket-сервер на VPS.
- **Пульт ведущего с телефона** — использует тот же room-слой: чистый экран показа
  без элементов управления, все действия (старт отбора, next, undo) — с отдельного
  устройства. Дешёвая надстройка поверх уже построенного транспорта из Фазы 2.
- **Лендинг + авторизация ведущего** (опционально, решить перед стартом Фазы 2 —
  см. открытые вопросы) — профиль хранит списки команд, брендинг шоу, историю
  сессий на сервере вместо localStorage.

### Фаза 3 — бэклог, не проектируем сейчас

- **Захват звука другой вкладки браузера + анализ.** Технический нюанс, который
  стоит держать в голове заранее: обычная веб-страница не может тихо «подключиться»
  к звуку чужой вкладки — это или отдельное browser-расширение (`chrome.tabCapture`),
  или ручной шаринг вкладки через `getDisplayMedia({ audio: true })` (пользователь
  сам выбирает вкладку в системном пикере). После захвата — распознавание речи
  (Web Speech API или серверный STT) и анализ текста (частые слова, вопросы без
  ответа — реалистично через LLM-суммаризацию, а не эвристики). Это отдельный
  подпроект, не блокирует Фазы 1–2.

## 5. Технический стек — рекомендация

Держим минимально достаточное, без лишней смены стека:

- Фронт: React + TS + Vite — как сейчас, меняется внутренняя архитектура, не
  инструменты.
- State/оркестрация показа: XState (или сравнимая явная state-machine библиотека)
  вместо самодельного reducer+useState.
- Real-time (Фаза 2): лёгкий Node-сервис (Fastify/uWebSockets) с WebSocket,
  session-state в памяти или Redis (сессии эфемерные, персистентная БД не нужна,
  пока не подключена авторизация).
- Авторизация/профиль (если решим делать в Фазе 2): минимальная — email+magic-link
  или пароль, без сложных ролей; Postgres/SQLite для профиля и списков команд.
- Деплой: фронт — статика (GitHub Pages/Vercel/Cloudflare Pages); WebSocket-сервис
  и (если будет) auth-бэкенд — на VPS пользователя, через Docker Compose, деплой по
  git-workflow (см. правила деплоя в CLAUDE.md).

## 6. Дизайн-бриф: главный экран ведущего (Фаза 1, приоритет №1)

Это фрагмент можно передать отдельно в дизайн-сессию (например, через `design`-скилл)
до начала кодирования — заказчик прямо просит сначала «поразмыслить над дизайном».

**Состояния экрана** (управляются show-machine из п. 2.1):

1. **Idle** — между отборами / до старта. Фон — мягкая фирменная анимация (лёгкая
   версия текущего `AmbientField`, но как «личность» шоу, а не только во время
   механики). По центру — крупное **настраиваемое название шоу** (текст задаётся
   в админке, сохраняется в настройках), под ним — второстепенная информация
   (сколько команд осталось / название текущей темы).
2. **Prerolling** — анти­сипация перед стартом (текущий drumroll-паттерн сохраняем),
   название шоу приглушается/уходит на задний план.
3. **Running** — сцена механики на весь экран (full-bleed), название шоу скрыто
   или сведено к минимальному лого в углу.
4. **Revealing** — кинематографичный реванш результата (имя/цвет команды, частицы),
   по теме оформления.
5. **Cleared / ожидание next** — возврат к idle-виду с обновлённым счётчиком.

**Панель управления:**

- Единая **нижняя панель**, докнутая по низу экрана: кнопка запуска отбора, next/
  undo, переключатель истории, переход в админку, переключатель темы (если нужен
  быстрый доступ), кнопка **«На весь экран»**.
- Кнопка полноэкранного режима — явная, видимая (не только хоткей `F`, как сейчас):
  Fullscreen API на контейнере показа, иконка отражает текущее состояние
  (войти/выйти), убирает браузерный chrome для чистого шаринга в Zoom/Meet/OBS.
- Панель по умолчанию видима в Idle; в Running/Revealing — либо остаётся тонкой
  полоской, либо автоматически уходит в полупрозрачный fade и появляется по hover/
  движению мыши (решить в самой дизайн-сессии — не жёстко фиксируем здесь).

**Тема/бренд:** название шоу, цветовая тема и (в будущем) логотип — конфигурируются
в админке и должны выглядеть как часть единого «фирменного» видео-шоу, а не как
отдельная функция поверх интерфейса.

## 7. Открытые вопросы — нужно решить до/во время дизайн-сессии

1. **Оценки выступлений от зрителей** — заказчик сам отметил это как спорную идею.
   Рекомендация: делать по умолчанию выключенным флагом в админке, начинать только
   с реакций (эмодзи), оценки — отдельное решение продукта позже, не блокирует MVP.
2. **Авторизация в Фазе 2** — действительно ли нужна, или session-code без
   аккаунтов достаточно для зрительской страницы и пульта? Если нет острой
   необходимости хранить конфиг между устройствами — можно отложить.
3. **Название/бренд нового проекта и репозитория** — остаётся «Sprint Review Show»
   или меняется вместе с переработкой?
4. **Объём Фазы 1 по механикам** — сколько из 14 переносим в первом срезе (весь
   список сразу против 2–3 «флагманских», чтобы быстрее дойти до работающего
   вертикального среза).

## 8. Предлагаемые следующие шаги

1. Дизайн-сессия по разделу 6 (главный экран) — до кода.
2. Создание нового репозитория, перенос кусков из раздела 3.
3. Реализация show-machine + unified engine + manifest на 2–3 механиках.
4. Только после этого — Фаза 2 (room-слой, зрительская страница, пульт).
