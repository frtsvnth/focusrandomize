# Спецификация: следующее поколение Sprint Review Show

> Черновик для нового отдельного репозитория. Документ рассчитан на то, что его
> откроет Claude Code (или другой агент) без контекста этого обсуждения — поэтому
> здесь есть и «зачем», и «что именно», а не только тезисы.
>
> **Статус (сентябрь 2026):** новая версия выпущена — Who Goes Next доступен по
> адресу <https://sme.pupupu.cloud/whogoesnext/>. Этот документ — проектная
> спецификация, по которой она собиралась.

## 1. Контекст

Текущий проект (`focusrandomize`, product-имя «Sprint Review Show») — статический
SPA-инструмент для гейміфицированного выбора очередности команд на Sprint Review:
14 визуальных механик отбора (колесо, гонки, лабиринт и т.д.), presenter-режим для
шаринга экрана, admin-панель, 5 тем, звук, localStorage-хранилище.

Рыночный вывод из ресёрча: инструменты-рандомайзеры (Wheel of Names и клоны) — это
голый спиннер без шоу; scrum-тулы (Geekbot, Standuply, Parabol) — геймификация без
визуального шоу. Никто не соединяет «инструмент ритуала» с полноценным зрелищем
(сюжет, саспенс, 3D, звук). Это и есть актив, который новая архитектура должна
защищать и усиливать.

**Решение:** новый проект — отдельный репозиторий, где презентационный слой
(обвязка, оркестрация показа, разделение ролей) переделывается первым, а сами
механики переносятся позже, по одной, на новый фундамент.

## 2. Архитектурные решения (взяты за основу — «вариант Б»)

1. **Единая show-machine.** Весь цикл показа (`idle → prerolling → animating →
   revealing → cleared`) — один явный state machine (state и переходы описаны в коде
   декларативно, кандидат — XState), а не смесь reducer-state и локального
   `useState` компонента, как сейчас. Это убирает класс багов рассинхрона
   анимации/результата, который уже проявлялся в текущем репо (hideSeek: «seeker
   turns before found»).
2. **Один движок механик.** V1 отбрасывается, остаётся только V2-подход (канвас/
   Three.js/Phaser, частицы, процедурный звук). Дублирование адаптеров и
   `MECHANIC_META` на два движка — не нужно.
3. **Presentation kit.** Частицы, canvas-утилиты, звуковой движок, темы — общий
   внутренний пакет с явным API, а не россыпь утилит внутри `mechanics-v2/engine`.
4. **Manifest-регистрация механик.** Каждая механика регистрируется одним файлом
   (id, метаданные, превью, точка входа), без правок в нескольких местах при
   добавлении новой.
5. **Room/session слой (новое).** Единый real-time «канал показа» — по коду сессии,
   без обязательной привязки к аккаунту. Изначально нужен для зрительской страницы
   (п. 4 ниже), но спроектирован достаточно универсально, чтобы позже тем же
   каналом мог быть пульт ведущего с телефона — это один и тот же transport
   (typed pub/sub поверх WebSocket), а не две отдельные подсистемы.

Бэкенд теперь допустим (пользователь готов развернуть на своём VPS) — это снимает
прежнее ограничение «только статический SPA» и открывает real-time функциональность.

## 3. Что переносим из текущего репозитория как есть

- `domain/schema.ts` + zod-валидация — модель данных проверенная, менять не за чем.
- `engine/selectionEngine.ts` — чистая логика выбора команды, уже покрыта тестами.
- Идея адаптерного контракта механики: `{ teams, targetTeam, seed, reducedMotion,
  onComplete }` — простой и удачно спроектированный интерфейс, сохраняем как базу
  нового manifest-формата.
- Ассеты и их пайплайн (Kenney-модели + CREDITS-файлы).

Всё остальное в презентационном слое — оркестрация показа, admin/controller UX,
V1/V2 развилка — пишется заново под новую архитектуру.

## 4. Фазы разработки

### Фаза 1 — MVP нового репозитория (делаем в первую очередь)

Именно то, что попросил заказчик как обязательное «прямо сейчас»:

- Show-machine + унификация движка механик (п. 2.1–2.3 выше), перенос 2–3 самых
  сильных механик как первый вертикальный срез (не все 14 сразу).
- **Полная переработка главного экрана ведущего** — дизайн-бриф в разделе 6
  уже реализован как кликабельный HTML/CSS/JS-прототип
  (`~/randomize-new-design`), см. оценку интеграции в разделе 7. Это первый
  видимый результат нового проекта, и переносить его в React/TS — следующий
  конкретный шаг Фазы 1.
- Admin-панель — минимальный перенос текущей функциональности (команды, сценарий
  очерёдности, темы, бэкап), без новых фич.
- Деплой: фронт может остаться статикой (GitHub Pages/Vercel), бэкенд для
  real-time — пока не обязателен, если Фаза 2 не стартовала одновременно.

### Фаза 2 — интерактивный слой и профиль ведущего

- **Зрительская страница** (`/join/<code>` или аналог) — участники команд, которые
  сейчас не выступают, заходят с телефона по коду сессии (без обязательной
  регистрации) и могут:
  - отправлять реакции (эмодзи-вспышка), которые всплывают на главном экране;
  - (опционально, за флагом в админке — см. открытые вопросы) ставить оценку
    выступлению;
  - после ceremony — видеть результаты/историю сессии.
  Технически: room/session слой из п. 2.5, WebSocket-сервер на VPS.
- **Пульт ведущего с телефона** — использует тот же room-слой: чистый экран показа
  без элементов управления, все действия (старт отбора, next, undo) — с отдельного
  устройства. Дешёвая надстройка поверх уже построенного транспорта из Фазы 2.
- **Лендинг + авторизация ведущего** (опционально, решить перед стартом Фазы 2 —
  см. открытые вопросы) — профиль хранит списки команд, брендинг шоу, историю
  сессий на сервере вместо localStorage.

### Фаза 3 — бэклог, не проектируем сейчас

- **Захват звука другой вкладки браузера + анализ.** Технический нюанс, который
  стоит держать в голове заранее: обычная веб-страница не может тихо «подключиться»
  к звуку чужой вкладки — это или отдельное browser-расширение (`chrome.tabCapture`),
  или ручной шаринг вкладки через `getDisplayMedia({ audio: true })` (пользователь
  сам выбирает вкладку в системном пикере). После захвата — распознавание речи
  (Web Speech API или серверный STT) и анализ текста (частые слова, вопросы без
  ответа — реалистично через LLM-суммаризацию, а не эвристики). Это отдельный
  подпроект, не блокирует Фазы 1–2.

## 5. Технический стек — рекомендация

Держим минимально достаточное, без лишней смены стека:

- Фронт: React + TS + Vite — как сейчас, меняется внутренняя архитектура, не
  инструменты.
- State/оркестрация показа: XState (или сравнимая явная state-machine библиотека)
  вместо самодельного reducer+useState.
- Real-time (Фаза 2): лёгкий Node-сервис (Fastify/uWebSockets) с WebSocket,
  session-state в памяти или Redis (сессии эфемерные, персистентная БД не нужна,
  пока не подключена авторизация).
- Авторизация/профиль (если решим делать в Фазе 2): минимальная — email+magic-link
  или пароль, без сложных ролей; Postgres/SQLite для профиля и списков команд.
- Деплой: фронт — статика (GitHub Pages/Vercel/Cloudflare Pages); WebSocket-сервис
  и (если будет) auth-бэкенд — на VPS пользователя, через Docker Compose, деплой по
  git-workflow (см. правила деплоя в CLAUDE.md).

## 6. Дизайн-бриф: главный экран ведущего (Фаза 1, приоритет №1)

Это фрагмент можно передать отдельно в дизайн-сессию (например, через `design`-скилл)
до начала кодирования — заказчик прямо просит сначала «поразмыслить над дизайном».

**Состояния экрана** (управляются show-machine из п. 2.1):

1. **Idle** — между отборами / до старта. Фон — мягкая фирменная анимация (лёгкая
   версия текущего `AmbientField`, но как «личность» шоу, а не только во время
   механики). По центру — крупное **настраиваемое название шоу** (текст задаётся
   в админке, сохраняется в настройках), под ним — второстепенная информация
   (сколько команд осталось / название текущей темы).
2. **Prerolling** — анти­сипация перед стартом (текущий drumroll-паттерн сохраняем),
   название шоу приглушается/уходит на задний план.
3. **Running** — сцена механики на весь экран (full-bleed), название шоу скрыто
   или сведено к минимальному лого в углу.
4. **Revealing** — кинематографичный реванш результата (имя/цвет команды, частицы),
   по теме оформления.
5. **Cleared / ожидание next** — возврат к idle-виду с обновлённым счётчиком.

**Панель управления:**

- Единая **нижняя панель**, докнутая по низу экрана: кнопка запуска отбора, next/
  undo, переключатель истории, переход в админку, переключатель темы (если нужен
  быстрый доступ), кнопка **«На весь экран»**.
- Кнопка полноэкранного режима — явная, видимая (не только хоткей `F`, как сейчас):
  Fullscreen API на контейнере показа, иконка отражает текущее состояние
  (войти/выйти), убирает браузерный chrome для чистого шаринга в Zoom/Meet/OBS.
- Панель по умолчанию видима в Idle; в Running/Revealing — либо остаётся тонкой
  полоской, либо автоматически уходит в полупрозрачный fade и появляется по hover/
  движению мыши (решить в самой дизайн-сессии — не жёстко фиксируем здесь).

**Тема/бренд:** название шоу, цветовая тема и (в будущем) логотип — конфигурируются
в админке и должны выглядеть как часть единого «фирменного» видео-шоу, а не как
отдельная функция поверх интерфейса.

## 7. Прототип главного экрана (`randomize-new-design`) — оценка интеграции

По разделу 6 уже собран рабочий кликабельный прототип: отдельная папка
`~/randomize-new-design` (вне этого репозитория), статический HTML/CSS/
vanilla-JS без сборки — `index.html`, `css/show.css` (~1400 строк),
`js/show.js` (~1100 строк, вся show-machine и админка), `js/mechanics.js`
(манифест механик + точка интеграции движков).

**Вывод: направление подтверждено, прототип берём за основу верстки и
поведения главного экрана, но переносим в React/TS, а не подключаем как есть.**

### Что переносится почти без изменений

- **Дизайн-токены полностью совместимы с текущим репо.** `--bg`,
  `--surface`, `--surface-2`, `--text`, `--accent` и сами 5 тем (dark/light/
  neon/retro/space) в `css/show.css` — те же имена и те же hex-значения, что
  в [src/index.css](src/index.css). Это не новый бренд поверх старого, а
  прямое продолжение — конфликтов при переносе не будет.
- Добавлена типографика поверх текущей (только Inter): `--font-display`
  (Unbounded) для заголовков, `--font-mono` (JetBrains Mono) для
  технических элементов (state-chip, счётчики). Осознанное усиление, не
  случайный выбор — переносим вместе с остальными токенами.
- **Форма state-machine подтверждена как есть**: `idle → prerolling →
  running → revealing → cleared` — 1:1 совпадает с разделом 2.1/6. Менять
  не нужно, реализуем эти же фазы через XState.
- HTML-структура и CSS-классы (`docs`/`dock`, `drawer-teams`,
  `drawer-admin`, `mech-popup`, `logo-layer`) — годный референс верстки,
  можно переносить в JSX почти дословно, меняя только событийную модель.
- **Новая секция бренда шоу** — логотип-подложка (inline SVG, мозаика
  полупрозрачных плиток, настройки прозрачности/размера/плотности) — удачное
  расширение раздела 6 «тема/бренд», в исходном дизайн-брифе было только
  название. Добавляем в объём Фазы 1 как есть.
- Плейсхолдер «Оценки зрителей» в админке (переключатель, по умолчанию
  выключен) — ровно то, что было рекомендовано в разделе 8 (открытый вопрос
  №1) для Фазы 2. В прототипе он декоративный (ни на что не влияет) — при
  переносе в Фазе 1 либо оставляем таким же неактивным заглушечным
  переключателем, либо прячем до появления реального audience-слоя в Фазе 2,
  чтобы не создавать у ведущего ложное ощущение работающей функции.

### Что нужно доработать при переносе

- **Прототип — vanilla DOM (`document.getElementById` + прямые
  мутации), не React.** `js/show.js` — это описание поведения и раскладки
  «как должно быть», а не код для импорта. Переносим логику в React-компоненты
  + XState-машину (раздел 2.1), используя `show.js` как построчную спецификацию
  переходов, хоткеев (`Пробел`, `F`, `Esc`) и localStorage-ключей
  (`srs:teams`, `srs:theme`, `srs:show-title`, `srs:mechanics-enabled` и т.д.
  — полный список см. в `README.md` прототипа).
- **Важная логическая неточность, которую нельзя переносить как есть:**
  в прототипе `runMechanic()` запускает механику с `targetTeam: null` и
  победитель выбирается ПОСЛЕ анимации, случайно
  (`js/show.js:246,266`). В реальном движке всё наоборот и это принципиально:
  `selectNextTeam` (раздел 3, `engine/selectionEngine.ts`) выбирает команду
  ДО показа механики, а сама механика лишь визуально ведёт к уже известному
  результату — на этом держится «управляемая случайность» (scripted order,
  pinned-next, честный random как отдельный режим). При переносе обязательно
  вызывать selection engine до монтирования механики и передавать готовый
  `targetTeam`, как в текущем `MechanicAdapterProps`.
- **Контракт механик у прототипа близкий, но не идентичный.**
  `Mechanics.register(id, ({ teams, targetTeam, seed, reducedMotion,
  onComplete, container }) => {...})` — те же поля, что в
  [src/mechanics/adapter.ts](src/mechanics/adapter.ts), плюс `container`
  (DOM-узел для монтирования) вместо React-компонента. Учитывая, что сами
  V2-движки (Phaser/Three.js) и так императивно монтируются на контейнер
  внутри `useEffect`, адаптация несложная — но нужно явно решить: механики
  остаются React-компонентами, монтируемыми в `#mech-frame` через ref, или
  тоже становятся императивными `register()`-функциями по образцу прототипа
  (второе ближе к тому, что уже показал прототип, и проще для manifest-подхода
  из раздела 2.4).
- **Схему настроек нужно расширить.** Новые поля из прототипа (`header`,
  `indicators`, `logo-on/svg/opacity/size/density`) не существуют в текущем
  [src/domain/types.ts](src/domain/types.ts) (`Settings`) — добавить туда и
  в zod-схему (`src/domain/schema.ts`) при переносе. `show-block-open` и
  `admin-expanded` — чисто UI-стейт (как нынешний `ui.historyVisible`), в
  схему валидации их включать не обязательно.
- **Дефолтные включённые механики у прототипа урезаны нарочно** (`wheel`,
  `slot`, `race` — чтобы попап механик не был пустым в демо), README сам это
  оговаривает. При переносе возвращаем реальный дефолт из
  `getInitialState()` (`wheel, slot, race, claw, cards, stickman, gladiator`).
- Собственные `drawAmbient`/`burst`-канвасы в прототипе дублируют то, что уже
  есть в `mechanics-v2/engine/AmbientField.tsx` и `particles.ts`. При переносе
  — не тащить вторую реализацию, а свести обе в общий «presentation kit» из
  раздела 2.3, взяв за основу то, что лучше визуально (сравнить на практике,
  а не решать заранее).

## 8. Идеология WhoGoesNext — что берём, что нет

Заказчик разобрал похожий рыночный продукт (WhoGoesNext) и прислал разбор его
подхода. Доступа к их коду нет — разбор основан на публичном UX/копирайтинге,
поэтому ниже речь о **паттернах продукта**, не о технической реализации.
Технические детали (Phaser/Three.js API) агент реализует опираясь на уже
существующую архитектуру проекта, а не на этот раздел.

### Берём

- **Каждая механика — законченная мини-история, а не рандомная анимация.**
  Формальный обязательный контракт трёх тактов для V2-механики (актуален и для
  уже существующих, и для будущих):
  1. *Ожидание (setup beat)* — короткая фаза, где видно всех участников разом,
     до начала интриги.
  2. *Нарастание (build-up)* — темп/напряжение растёт нелинейно, с ускорением к
     кульминации, независимо от конкретной механики; здесь же уместен приём
     ложной тревоги (fakeout) — на миг кажется, что определится не тот исход.
  3. *Раскрытие (reveal)* — обязателен фирменный сквозной приём (см. ниже), а
     не полностью самобытный финал у каждой механики.
  Перед реализацией новой/переделываемой механики агент должен уметь ответить
  одним предложением: «Это [метафора], в которой [что нарастает] и [как
  раскрывается результат]». Нет ответа — механика не готова к разработке.
- **Фирменный сквозной приём раскрытия (brand signature).** 1–2 визуально-
  звуковых элемента, обязательных в финале ЛЮБОЙ механики независимо от темы и
  жанра — в текущем проекте это уже кинематографичный reveal + процедурный звук
  из V2-движка, эту базу не изобретаем заново. Реализовать как переиспользуемый
  общий модуль (часть presentation kit из раздела 2.3), который вызывается в
  конце каждой механики поверх её уникальной части — не копипастить в каждый
  адаптер.
- **Честность механики как часть интерфейса, а не только бэкенда.** Помимо
  корректной работы scripted mode, нужен явный доброжелательный UI-сигнал
  зрителю о принципе игры (например, короткая надпись в начале раунда о том,
  что распределение честное). Это требование к UI-слою поверх механики, не к
  коду выбора.
- **Быстрый старт отдельно от полной админки.** Для сценария «просто быстро
  выбрать»: список участников уже есть (сессия) → выбрать механику → запустить,
  без обязательного похода в полную админ-панель. Полная админка (сценарии,
  PIN, темы, бренд-настройки) остаётся как отдельный слой для настройки, не для
  ежедневного использования — совпадает с разделением «пульт/экран» из раздела 2.5.
- **Локальные темы поверх глобальной — точечно, необязательно.** Там, где это
  дёшево реализовать (например, механика с колесом/спином, где смена палитры —
  по сути замена набора цветов), можно добавить 2–3 локальных визуальных
  варианта поверх глобальной темы приложения. Не обязательное требование ко
  всем механикам — применять выборочно, где эффект/усилие оправданы.
- **Копирайтинг про эмоцию/момент, а не про функцию/конфигурацию.** При
  обновлении интерфейса (не кода механик) переписывать подписи и подсказки в
  духе «сейчас произойдёт что-то интересное», а не нейтрально-технически.

### Сознательно не берём

- Аккаунты, тарифы, лимиты, облачное сохранение списков как обязательную часть
  MVP — в новом репозитории это Фаза 2 и то опционально (раздел 4/10, открытый
  вопрос про авторизацию), не берём бездумно только потому что у референса есть.
- Пост-реролл мини-игры на угадывание (факт/капс, флаги и т.п.) — отдельный
  жанр контента (викторины), непропорционально расширяет скоуп для кейса
  Sprint Review/agile-ритуалов.
- Буквальное копирование названий или иконок-эмодзи механик референса — у
  проекта уже есть более богатая и самобытная номенклатура (Трактор,
  Гладиаторы, Похищение, Стас идёт искать) — её и развиваем дальше, а не
  подгоняем под чужую.

## 9. Организация механик в новом репозитории — для независимой доработки

Заказчик отдельно попросил: механики будут дорабатываться/переписываться и
дальше, отдельно от остального проекта — раскладка должна быть такой, чтобы
менять одну механику полностью (баг, редизайн, замена движка) не задевало
остальные и презентационный слой.

Принцип: **каждая механика — самодостаточная папка-плагин.**

```
src/mechanics/<id>/
  index.ts        — register(id, run) для манифеста + метаданные (label, description, isNew)
  engine.ts        — вся Phaser/Three.js-логика конкретной механики (или несколько файлов —
                      как сейчас в toyRace/tractor/hideSeek с подпапками logic/, sceneBuild/)
  assets/           — свои текстуры/модели, если не переиспользуются другими механиками
README.md (по желанию) — если у механики нетривиальная логика (как сейчас у hideSeek)
```

- Между папками механик — никаких прямых импортов друг у друга. Общий код
  (частицы, звук, canvas-утилиты, фирменный reveal-модуль из раздела 8) — только
  через `presentation-kit` (раздел 2.3), импортируемый, а не копируемый.
- `register()` получает контейнер и данные (раздел 7, контракт из прототипа) и
  ничего не знает о show-machine, admin-панели или React-дереве снаружи —
  значит механику можно unit-тестировать, переписать с нуля или временно
  выключить, не трогая ничего вне её папки.
- Манифест (`src/mechanics/index.ts` или `manifest.ts`) — единственное место,
  которое перечисляет все механики; при полной замене механики другой файл
  менять не нужно, кроме этой одной строки регистрации.
- Перенос с V1/V2-адаптеров текущего репозитория: берём только V2-версии
  (раздел 2.2 — V1 отбрасывается целиком), перекладываем их внутреннюю
  Phaser/Three.js-логику в `engine.ts` новой папки почти как есть, снаружи
  оборачиваем в `register()` вместо React-компонента.
